# DECISION MEETING FRAMEWORK

Main objective:

> Build Decision Meeting Framework as an operating system with a clear purpose, ownership, inputs, outputs, triggers and evidence that the system actually reduces friction.

## 1. CONTEXT
Define people/teams involved, work type, current tools/channels, cadence, volume, constraints, failure modes and success criteria.

## 2. DOMAIN STANDARD
Meetings are justified only when synchronous interaction creates value. Decisions, actions and context should be captured once and routed to the right channel. Async updates should reduce meeting load, not duplicate it.

## 3. INTEGRITY CHECKS
- meeting has a decision/discussion purpose
- attendees are necessary
- pre-read is available when needed
- agenda allocates decision time
- notes capture decision/rationale/action
- actions have owner/date
- async channels have clear use
- documentation has a source of truth

## 6. FAILURE MODES
Avoid meetings without decisions, notes without actions, unclear ownership, overloaded capacity, hidden queues, status duplication, knowledge trapped in people, and systems that require heroic memory.

## 7. REQUIRED OUTPUT
1. Current system map.
2. Purpose and owner.
3. Trigger/input/output logic.
4. Risks/failure modes.
5. Required matrices.
6. Operating cadence.
7. Escalation.
8. Improvement criteria.

End with **System Integrity Check** confirming the workflow reduces ambiguity and has measurable evidence of usefulness.
